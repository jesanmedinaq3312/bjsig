# Plan de remediación — BJSIGAPP

**Fecha:** 1 de noviembre de 2026  
**Alcance de este documento:** planificación basada en el backlog adjunto y una revisión de solo lectura del repositorio local. **No se modificó código ni se ejecutó SQL o cambios en Supabase.**

## Estado y restricciones

La vista previa de BJSIGAPP está activa y conectada localmente al proyecto Supabase BJSIG. Los valores de Preview están en `.env.local`, excluido por Git; no se guardaron en la configuración administrada del proyecto. Se confirmó el nombre y estado del proyecto, pero no se inspeccionaron tablas, filas, políticas ni funciones del Supabase desplegado.

La regla de negocio indicada por el usuario se toma como requisito: **solo el Dev Team está autorizado a acceder al portal de trabajadores**. La implementación actual parece permitir sesiones `worker` en ese portal; debe corregirse antes de considerar cerrado el riesgo. Cualquier migración o escritura sobre la base compartida queda fuera de este plan y requerirá revisión del SQL exacto, respaldo comprobable y aprobación expresa previa.

## Hallazgos que determinan el orden

1. **Bloqueo de autorización:** `src/App.tsx` y el flujo `src/views/WorkerAuth.tsx` admiten el portal para `isWorker`; además, `docs/authorization-contract.md` describe acceso propio de trabajadores. El preview de soporte usa una condición `isAdmin`, que no demuestra por sí sola que el actor pertenezca al Dev Team. La regla Dev Team-only debe aplicarse en rutas, funciones y acceso a datos, no solo ocultando pantallas.
2. **No se puede auditar todo desde este checkout:** faltan en el repositorio las funciones Edge `worker-auth`, `worker-gdpr`, `harassment-report-submit` y `honeytoken-check`, aunque hay consumidores locales. Antes de corregirlas o desplegarlas hay que recuperar y revisar sus fuentes reales.
3. **El estado remoto de RLS es desconocido:** el repo contiene migraciones incrementales, no un esquema completo; no se comprobó qué migraciones, grants, funciones auxiliares o políticas están activos en BJSIG.
4. **Riesgos prioritarios en el código local:** `canManageAccount` permite a un developer administrar ciertas cuentas de plataforma; `send-tenant-onboarding` admite URLs externas, acepta contraseña temporal y no limita claramente el tenant; `admin-user-manage` no exige AAL2 según política y aplica una regla de contraseña más débil que `passwordPolicy`; el generador de tarjetas QR inserta `companyName` mediante `document.write` sin escapar.
5. **Privacidad y auditoría:** el login de trabajadores solicita GPS antes de autenticar y prepara un payload con ID de dispositivo, fingerprint y otros metadatos; `log-activity` exige AAL2 de forma global y el cliente puede descartar eventos tras reintentos. El repositorio no demuestra que existan retención automática efectiva ni trazabilidad de lectura suficiente para denuncias.

## Puertas de aprobación y seguridad

- **Ahora:** únicamente este plan; no se cambió código, esquema, políticas, datos ni funciones desplegadas.
- **Antes de un cambio de base:** consulta de catálogo, dump de esquema, respaldo y restauración probada en staging; propuesta con SQL exacto, tablas/roles afectados, impacto, verificación y rollback. La aprobación del objetivo general no sustituye la aprobación del SQL concreto.
- **Antes de desplegar Edge Functions:** revisar sus fuentes completas, probarlas en staging y mostrar qué endpoints/secretos/redirects cambiarían.
- **Antes de políticas de privacidad o textos legales:** validación por asesor legal y fuente oficial. Este plan no es asesoría jurídica ni determina la fecha legal.
- **Antes de E2E CRUD:** ambiente aislado, identidades de prueba y cleanup por IDs creados por el test; no usar cuentas ni trabajadores reales.

## Decisiones que conviene cerrar en la siguiente etapa

1. Formalizar la lista exacta de roles Dev Team autorizados y qué significa acceso al portal: el requisito recibido se mantiene como Dev Team-only; la revisión deberá distinguir el login público de la autorización al portal y sus datos.
2. Precisar qué pueden hacer `operator` y `manager` sobre solicitudes y marcajes por operación y estado; el backlog identifica esa amplitud como pendiente de decisión.
3. Confirmar dominios oficiales para onboarding/CORS y si el proxy de entrada controla las cabeceras IP.
4. Acordar responsables, plazos y excepciones de retención, y validar GPS, dispositivo, canal Ley Karin y Ley 21.719 con asesoría legal.

Ningún SQL productivo se ejecutará sin la aprobación específica indicada arriba.
